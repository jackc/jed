# Generated columns — design

A **stored generated column** holds a value computed from the other columns of its own row:

```sql
CREATE TABLE line (
  qty   i32 NOT NULL,
  price decimal(10,2) NOT NULL,
  total decimal(12,2) GENERATED ALWAYS AS (qty * price) STORED
);
```

The engine computes `total` on every `INSERT` and recomputes it on every `UPDATE` that changes
`qty` or `price`. It is ordinary stored data on disk: reads, indexes, keys, and constraints see it
like any other column. The surface and behavior follow PostgreSQL 18 (CLAUDE.md §1). Every
deliberate divergence is listed in §9 and in the corpus override ledger.

## 1. Surface

```
column_def      ::= name type { column_constraint }
column_constraint ::= … | "GENERATED" "ALWAYS" "AS" "(" expr ")" "STORED"
```

The clause is a column constraint. It may sit among the column's other constraints in any order
(`NOT NULL`, `CHECK`, `UNIQUE`, `PRIMARY KEY`, `REFERENCES`, `COLLATE`), in `CREATE TABLE` and in
`ALTER TABLE … ADD COLUMN`.

Parse-level errors, all `42601` with PostgreSQL's messages:

| Input | Message |
|---|---|
| `GENERATED BY DEFAULT AS (expr)` | `for a generated column, GENERATED ALWAYS must be specified` |
| two generation clauses on one column | `multiple generation clauses specified for column "b" of table "t"` |
| a generation clause plus `DEFAULT` | `both default and generation expression specified for column "b" of table "t"` |
| a generation clause plus `GENERATED … AS IDENTITY` | `both identity and generation expression specified for column "b" of table "t"` |

**`STORED` is required.** PostgreSQL 18 also has `VIRTUAL` generated columns (computed on read,
never stored) and makes `VIRTUAL` the default when neither keyword is written. jed implements only
`STORED`. Both `VIRTUAL` and the bare form (no keyword) are `0A000` (`virtual generated columns
are not supported`). The bare form is rejected, not read as `STORED`, so that a later `VIRTUAL`
slice can give it PostgreSQL's meaning without changing what an existing statement does.

## 2. The generation expression

The expression is a scalar expression over the table's own columns. It is admitted at `CREATE
TABLE` (and `ADD COLUMN`) in this order:

1. **Structural pre-walk** (one depth-first walk before resolution, as for `CHECK` —
   [constraints.md §4.1](constraints.md)):
   - a subquery is `0A000` `cannot use subquery in column generation expression`;
   - an aggregate call is `42803` `aggregate functions are not allowed in column generation
     expressions`;
   - a window call (`OVER`) is `42P20` `window functions are not allowed in column generation
     expressions`;
   - a set-returning function is `0A000` `set-returning functions are not allowed in column
     generation expressions`;
   - a bind parameter `$N` is `42P02` `there is no parameter $N`.
2. **Column references.** Every column of the table is in scope, including columns declared after
   the generated column. An unknown column is `42703`. A reference to **another generated
   column** (or to itself) is `42P17` `cannot use generated column "c" in column generation
   expression`, with detail `A generated column cannot reference another generated column.`
3. **Name and type resolution** against the table's columns, with the column's declared type as
   the operand hint.
4. **Immutability.** The expression must be immutable under the same compositional analysis an
   expression index uses ([index-dependencies.md](index-dependencies.md) "Admission"). Any
   session, clock, entropy, or sequence dependency is `42P17` `generation expression is not
   immutable`.
5. **Assignment type.** The result must coerce to the column type by the assignment rule, else
   `42804` `column "b" is of type i32 but default expression is of type text` with hint `You will
   need to rewrite or cast the expression.` The message says "default expression", which is what
   PostgreSQL 18 prints for a generation expression too.

Two narrowings, both `0A000`, are follow-ons (§10):

- A **host function** in the expression. A stored generated value is derived from the function the
  way an index key is, so admitting one needs the index rule ([extensibility.md §8.1](extensibility.md)):
  an immutable declaration, a component identity, and a persisted dependency list on the column.
- An expression with a **timezone-data dependency** (a named zone, or a nonconstant zone
  expression). `AT TIME ZONE 'UTC'` and fixed offsets have none and are admitted. A persisted
  dependency list would be needed for the same reason as for an index.

The column may have any type an expression default may have, including composite, array, and range
types. A generated column may be `NOT NULL`, carry or appear in a `CHECK`, be a `PRIMARY KEY` or
`UNIQUE` member, be indexed, and be the referencing side of a foreign key.

**Foreign keys.** A foreign key whose referencing columns include a generated column may not have
an action that writes those columns. `ON UPDATE CASCADE`, `ON UPDATE SET NULL` and `ON UPDATE SET
DEFAULT` are `42601` `invalid ON UPDATE action for foreign key constraint containing generated
column`. `ON DELETE SET NULL` and `ON DELETE SET DEFAULT` are `42601` `invalid ON DELETE action for
foreign key constraint containing generated column`. `NO ACTION`, `RESTRICT` and `ON DELETE
CASCADE` are allowed. The check runs at `CREATE TABLE` and at `ALTER TABLE … ADD [CONSTRAINT] …
FOREIGN KEY`.

## 3. Writes

### 3.1 `INSERT`

A generated column accepts only `DEFAULT`:

- An `INSERT` whose target list names a generated column is `428C9` `cannot insert a non-DEFAULT
  value into column "b"`, detail `Column "b" is a generated column.`, unless every row of a
  `VALUES` source has the `DEFAULT` keyword in that column. This includes an omitted column list
  that covers the column positionally, and `INSERT … SELECT`. The check happens before any row is
  read, as in PostgreSQL's rewriter, so it fires even when the source is empty.
- `OVERRIDING SYSTEM VALUE` and `OVERRIDING USER VALUE` do not change this.

**Row build order** ([constraints.md §7](constraints.md) step 1, extended):

1. Build the base row in column order: each non-generated column takes its supplied value or its
   default, coerced and range-checked. A generated column's slot is a placeholder.
2. Compute each generated column in column order: evaluate its expression over the row from step 1
   (generated slots are never read, by §2), then coerce the result to the column type and typmod
   (`numeric(4,1)` rounds, `varchar(2)` raises `22001`). An evaluation error propagates as itself.
3. Enforce `NOT NULL` over the complete row in column order, then `CHECK`s, keys, and the rest of
   constraints.md §7.

So a generation expression's error beats a `NOT NULL` violation in an earlier base column
(PostgreSQL computes generated columns before `ExecConstraints`; oracle-checked).

### 3.2 `UPDATE`

`SET b = <expr>` on a generated column is `428C9` `column "b" can only be updated to DEFAULT`,
detail `Column "b" is a generated column.` `SET b = DEFAULT` is accepted and changes nothing on its
own.

A generated column is **recomputed exactly when one of the columns its expression references is a
`SET` target** of the statement (PostgreSQL's `ri_extraUpdatedCols` rule). The decision is per
statement, not per row, and is made from the statement text. Every row the statement updates
recomputes the same set of generated columns, even a row whose referenced values do not change.
Recomputation runs after the new row's assigned values are coerced and before `NOT NULL`, in
column order, by §3.1 step 2.

The same rule covers every path that updates a row:

- `INSERT … ON CONFLICT DO UPDATE` — the `SET` targets of the `DO UPDATE` clause.
- `MERGE … WHEN MATCHED THEN UPDATE` — that action's `SET` targets.
- A foreign key `ON UPDATE CASCADE` / `SET NULL` / `SET DEFAULT` or `ON DELETE SET NULL` / `SET
  DEFAULT` action on a child table — the child columns the action writes. (§2 forbids those
  columns from being generated, but a generated column may *reference* them.)
- An `UPDATE` through an updatable view — the base columns the view's targets map to.

### 3.3 Views

An updatable view exposes a generated base column like any other column. Writing it through the
view follows §3.1/§3.2 with the base column's name in the message. A view column default
(`ALTER VIEW … ALTER COLUMN … SET DEFAULT`) on such a column is a supplied value, so an `INSERT`
through the view that applies it is `428C9`, whatever the `OVERRIDING` clause (PostgreSQL's rewriter
substitutes the view default before it checks the base column).

### 3.4 `RETURNING`

`RETURNING` sees the computed values, since it evaluates over the validated candidate rows.

### 3.5 Cost

Evaluating a generation expression is ordinary metered expression work: `operator_eval` per
interior node (and `decimal_work` where decimal arithmetic runs), per generated column computed,
per candidate row ([cost.md](cost.md) §3). As for a `CHECK`, an `INSERT … VALUES` into a table with
a generated column therefore costs more than zero.

## 4. DDL

### 4.1 `ALTER TABLE … ADD COLUMN … GENERATED ALWAYS AS (expr) STORED`

The table is rewritten ([alter.md §3.1](alter.md)) and each existing row's new value is the
expression evaluated over that row, coerced by §3.1 step 2. The expression may reference any column
of the table as it stands after the statement's earlier actions, but not a column added by the same
statement (`0A000` this slice, a follow-on). Then the ordinary `ADD COLUMN` validation runs (`NOT
NULL`, `CHECK`, `UNIQUE`, `PRIMARY KEY`).

### 4.2 `ALTER COLUMN … DROP EXPRESSION [IF EXISTS]`

Turns a generated column into an ordinary column that keeps its stored values. Catalog-only. On a
column that is not generated it is `55000` `column "c" of relation "t" is not a generated column`,
or with `IF EXISTS` a notice and no change.

### 4.3 Other `ALTER COLUMN` forms on a generated column

| Form | Result |
|---|---|
| `SET DEFAULT` | `42601` `column "b" of relation "t" is a generated column`, hint `Use ALTER TABLE ... ALTER COLUMN ... SET EXPRESSION instead.` |
| `DROP DEFAULT` | `42601`, same message, hint `Use ALTER TABLE ... ALTER COLUMN ... DROP EXPRESSION instead.` |
| `SET EXPRESSION AS (expr)` | `0A000` this slice (a follow-on, §10) |
| `TYPE …` | `0A000` this slice (a follow-on, §10). With `USING` it is `42611` `cannot specify USING when altering type of generated column`, as in PostgreSQL |
| `ADD GENERATED … AS IDENTITY` | the ordinary identity rules apply. A generated column has no default, so the identity's own gates decide |
| `SET NOT NULL` / `DROP NOT NULL` | allowed, as for any column |

### 4.4 Columns a generated column references

- **`RENAME COLUMN`** rewrites the stored generation text, as for every stored expression
  ([alter.md §2.2](alter.md)).
- **`ALTER COLUMN … TYPE`** on a referenced column is `0A000` `cannot alter type of a column used by
  a generated column`, detail `Column "a" is used by generated column "b".`
- **`DROP COLUMN`** on a referenced column is `2BP01` `cannot drop column a of table t because other
  objects depend on it`, detail `column b of table t depends on column a of table t`, hint `Use DROP
  ... CASCADE to drop the dependent objects too.` With `CASCADE` the generated column is dropped
  too (PostgreSQL also prints the notice `drop cascades to column b of table t`; jed has no
  notice channel for DDL).

## 5. Introspection

`jed_columns` ([introspection.md §5](introspection.md)) gains a trailing column:

```
generation_expression text   -- the generation expression's canonical text for a generated
                             --   column, else NULL
```

The name and meaning follow PostgreSQL's `information_schema.columns.generation_expression`. The
text is the stored canonical token text (the same rendering a `CHECK` persists), so it is
`a * 2`, not PostgreSQL's deparsed `(a * 2)`. A generated column's `column_default` is NULL, as in
PostgreSQL.

The CLI dump ([cli.md §3](cli.md)) writes `GENERATED ALWAYS AS (<text>) STORED` for a generated
column.

## 6. Persistence (`format_version` 55)

The per-column catalog entry's `flags` byte ([../fileformat/format.md](../fileformat/format.md))
gains **bit 7 `is_generated`**. A generated column sets bit 7 and bit 3 (`default_is_expr`), and
the entry's expression-text slot (`default_expr_len` + `default_expr`) holds the generation
expression's canonical text. A generated column never sets bit 2 (`has_default`) or bit 4
(`is_identity`). Bit 7 with bit 3 clear, or with bit 2 or bit 4 set, is `XX001`.

In memory a generated column has **no default**: the expression lives in its own field, so no
default-applying path can mistake it for one.

The text re-parses at load. Text this binary's parser rejects is kept unparsed and byte-for-byte,
and any statement that would compute the column fails with `XX003` (`INSERT`, and an `UPDATE` that
recomputes it), as for an unparsable expression default
([unparsable-definitions.md](unparsable-definitions.md) §3.3).

Version 55 changes no other bytes. Older readers treated bit 7 as reserved and trusted the other
bits, so they would read a generated column as an expression default. The version bump makes them
refuse the file instead.

## 7. Determinism

A generation expression is immutable (§2), so its value is a pure function of the row's other
values. Evaluation order is fixed (column order), the recompute set is a function of the statement
text, and cost is metered per evaluation. Nothing here depends on iteration order, the clock, or
the entropy seam (CLAUDE.md §8).

## 8. Tests

The contract is the corpus: `spec/conformance/suites/ddl/generated_column.test` (surface, admission
errors, `ALTER TABLE`) and `spec/conformance/suites/dml/generated_column.test`
(writes, recompute rule, `ON CONFLICT`, `MERGE`, views, FK actions, cost). Both are
oracle-checked. `ddl/generated_column_jed.test` holds the §9 divergences and
`introspection/jed_columns_generated.test` the `jed_columns` column. The file-format golden
`generated_table.jed` pins the v55 bytes, and the forged `malformed_generated_flags.jed`
(`storage/malformed_generated_flags.test`) pins the `XX001` for a forbidden flag combination.

## 9. Divergences from PostgreSQL

- **No `VIRTUAL`, and the bare form is rejected** (`0A000`, §1). PostgreSQL 18 makes the bare form
  virtual.
- **`generation_expression` text** is jed's canonical token text, not PostgreSQL's deparse (§5).
  jed's `jed_columns` has no PostgreSQL counterpart to oracle-check.
- **Admission micro-order.** As for `CHECK`, the structural rejections run in one pre-walk before
  name resolution, so an expression with two different errors may report a different (equally
  valid) one than PostgreSQL.
- **Host functions and timezone-dependent expressions** are `0A000` (§2) where PostgreSQL admits
  any immutable function.
- **`SET EXPRESSION`, `ALTER COLUMN … TYPE` on a generated column**, and a generated `ADD COLUMN`
  referencing a column added by the same statement are `0A000` (§4).

## 10. Follow-ons

- `VIRTUAL` generated columns.
- `ALTER COLUMN … SET EXPRESSION AS (expr)` (a table rewrite) and `ALTER COLUMN … TYPE` on a
  generated column (recompute under the new type).
- Host functions in a generation expression, under the index rule, with a persisted dependency
  list on the column ([extensibility.md §8.1](extensibility.md)).
- Timezone-dependent generation expressions, with a persisted timezone dependency list
  ([index-dependencies.md](index-dependencies.md)).
- A generated `ADD COLUMN` that references a column added earlier in the same statement.
