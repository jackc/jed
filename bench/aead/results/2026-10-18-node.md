# Node engine comparison (2026-10-18 UTC)

Existing native Rust/Node-API binding versus independent TypeScript and Rust/WASI, rebuilt from this checkout. Seven 300 ms samples after one 300 ms warmup per case, CPU 0 on the Intel Core Ultra 9 285K, Node v26.10.0. Workers run sequentially. The initial five-by-100-ms run is retained separately; the longer run checks variability, especially on the TypeScript aggregate.

## Measured boundary

Each backend creates its own file with identical schema and 10,000 integer rows, using one setup transaction. Setup is excluded. All queries are prepared once and return materialized text rows to JS. Timings include each binding's conversion: TS Values are rendered, WASM's text result buffer is decoded, native Node-API bigint rows are decoded and normalized to text. This is a comparison of present end-to-end APIs, not an isolated comparison of code generators. There are no bound parameters in these five probes.

Both Rust wrappers use opt-level 3, LTO, one codegen unit and stripped symbols. The existing Node native addon uses its default page-service owner; TS and WASI use externally coordinated `locking=none`, with disjoint scratch files and no other accessors (WASI does not support the OS locks). The measured operations are warm reads, not cold reads, durable writes, multi-process access, concurrent read throughput, encryption, startup, or browser OPFS. Results are not directly interchangeable with the earlier in-memory WASM/TS probe.

Complete result arrays agree across all three backends before and after each case. This validates the measured queries, not the complete binding API. The native binding remains experimental and supports a smaller host surface than the independent TS core.

| Query | TypeScript µs | Rust/WASM µs | Native Rust/Node-API µs |
|---|---:|---:|---:|
| constant | 0.999 | 1.273 | 2.780 |
| point | 2.850 | 1.927 | 3.383 |
| aggregate | 7439.773 | 1257.457 | 2547.053 |
| sort | 1679.446 | 649.210 | 556.111 |
| return1000 | 307.829 | 443.757 | 198.680 |

The native wrapper wins the sort and 1,000-row return in this set. TS wins the constant query; WASM wins the point and aggregate. The native aggregate remaining slower than WASM reproduced in both runs; its cause is **not profiled**. The different wrappers, host configurations, pointer widths and runtime implementations are candidates to investigate, not established explanations. Do not attribute the whole difference to boundary overhead, or claim native compilation always wins.

TypeScript aggregate measurements still vary; raw samples are retained rather than hiding that variability. No overall geometric mean from five selected reads should choose a default package. The broader historical write/concurrency evidence is in spec/design/benchmarks.md §7.3.

## Reproduce

```sh
JED_AEAD_SAMPLES=7 JED_AEAD_SAMPLE_MS=300 mise run bench:aead_node_compare
```

The task uses the already approved native binding dependencies, cached offline Cargo builds, and existing esbuild/@noble/hashes installations. Set JED_ESBUILD and JED_NOBLE_HASHES if needed. It requires the wasm32-wasip1 target and permission for the native database's local Unix-domain page-service socket. No new dependency or engine change was introduced. JSON records revision, sample timings, source hashes and artifact hashes; .jed scratch files stay under ignored bench/results/.
