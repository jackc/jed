# Go execution specialization: G2 and G3 continuation

This continues the [G1 investigation](../2026-10-19/report.md) on the same
research branch. G2 adds bounded composition and its closure control; G3 adds
an independently selectable precompiled scan loop. All remain opt-in. No Rust
or TypeScript implementation, SQL/API, planner policy, cost schedule, logical
memory schedule, dependency, or file format changes.

## Scope and correctness

G2 composes the G1 terminals and primitive leaves with value/filter AND, OR,
NOT, NULL tests, one-WHEN searched CASE and two-argument COALESCE. Arithmetic
still uses G1's small checked patterns. Casts, larger arithmetic patterns,
multiple WHEN arms, larger COALESCE lists, and nonprimitive types remain
ordinary complete-root fallbacks. The shared NoREC controls use multiple WHEN
arms so they remain independent fallbacks after CASE admission.

Preparation checks 192 nodes and depth 32 before allocating descriptors. Tests
cover the largest accepted node count/depth, one beyond each, wider plan root
counts, no allocation on oversized rejection, and no per-row kernel allocation.
Static descriptors contain no source/execution pointers. The closure variant
retains one closure per source node and a root wrapper, not the temporary static
graph; a weak-reference test checks that the graph is collectible while the
closure remains usable. Both variants reuse the original immutable plan-cache
publication/validity machinery.

G3 requires a fully admitted filter/projection bundle and no host read-ahead. It
selects a small cursor wrapper at setup, leaving fallback bundles on G2's
original row loop. The wrapper uses the same scan/point source, resolve masks,
cost meter, LIMIT/OFFSET state, output allocation and close implementation.
There is no survivor buffer, new batching, or extra cancellation poll. The
ordinary and untagged builds select the original cursor.

Verification completed:

- Complete Go corpus in ordinary, G2 selective/forced, forced closures, and G3
  selective/forced: each **678 memory passes / 2 skips** and **597 disk passes /
  83 skips**, no failures. These are files, not individual SQL statements.
- Default Go unit suite and the complete G3 Go unit suite.
- Combined forced G3/closures race tests for specialization, plan caches,
  custom plans, cancellation, query memory, depth and streaming.
- G3 forced resource suites with finite query memory and 256-byte work_mem:
  **28 memory passes / 2 skips**, **24 disk passes / 6 skips**.
- G3 NoREC: two seeds, **148 files / 1,628 query relations**, all pass.
- Expanded shared expression fixture regenerated byte-identically by the
  checkout's PostgreSQL oracle; all spec/codegen verification passed.
- Diagnostic root invocation counts, loop selection, output ownership, cache
  replacement/GC, changed bindings, interleaved and concurrent statement use,
  every small-expression statement/lifetime cost prefix, finite query-memory
  failures, LIMIT/OFFSET, and real file-read fault/cancellation order.

An initial selective G3 disk run overlapped NoREC's temporary-file cleanup and
reported missing generated files. The unaffected five modes passed; the entire
selective mode was rerun serially and passed. No engine change was needed. The
cancellation test's private meter injection now unwraps the experimental cursor
for access but still drives the selected G3 loop. Other cores and repository-wide
CI were not built/run for this Go-only research change.

## Measurement protocol

G2 was measured before implementing G3. Both matrices use clean production
`dfb0699f18e7c5bb120bc0f885f257791b19e2b9`, current untagged code, a same-source
ordinary control, and the candidate. G2 also includes pinned G1
`90e654fe9b206a5b63d332ea170709e453f5091f` and closure composition; G3 includes
a same-source G2 static control. Every archive receives the identical benchmark
source. Exact commands, tags, source hashes, environment and every sample are
in [g2/](g2/) and [g3/](g3/).

Go 1.27.1 linux/amd64, Intel Core Ultra 9 285K, default runtime/compiler options,
no PGO or affinity. The physical host is shared and timing is noisy. Binaries
build before timing; workers run sequentially in alternating order. Each matrix
uses five fresh process sets at **100 ms per workload**. Only suspicious lanes
get three additional **250 ms** sets with those exact binaries. No long soak
runs or outlier deletion. Diagnostic profiles are separate from decision data.

Each operation is a complete drained/checksummed query over 4,096 deterministic
rows, memory or reopened/warm file. LIMIT 16, finite cost, OFFSET, point hit/miss,
scalar, unsupported, columnar, ad-hoc and first-call controls remain. Both
parameter bindings' result checksums and exact costs agree across every timed
variant and process. File setup uses SkipFsync; this measures warm reads, not
cold I/O, write durability or whole-engine throughput.

The declared research gate remains 10% lower median on two target shapes with
four-of-five favorable pairs; investigate controls slower than 3%. CASE,
COALESCE and composed booleans are the new G2 targets. G3 must also demonstrate
an incremental improvement over G2, rather than receiving credit for G2's gains.

G2 has a useful boolean-filter gain (14.9% memory, 11.5% file, both 5/5), but
its other new targets are below the proposed 10% gate: COALESCE improves
9.6%/7.5%, CASE 4.8%/4.8%. Static composition generally wins arithmetic over
closures; neither representation consistently wins all conditional shapes.
Memory arithmetic is 11.5% slower with closures than with static kernels.

G2 retains warm allocation counts: 8,210 for arithmetic/CASE/COALESCE, 6,468
for the simple filter and 5,560 for composed boolean filtering. On the ad-hoc
arithmetic lane, clean uses 116 allocations, static G2 118 and closures 124;
first-call counts are 119, 121 and 127. Closure preparation therefore has a
measurable cost even though the graphs are collectible.

The first matrix showed file point-hit +6.1%, scalar +7.3%, unsupported +3.9%
and columnar +4.1% versus clean. Three targeted 250 ms sets reduced point-hit
to +2.9%, scalar to +2.6%, and reversed unsupported to -5.4%. Columnar remained
+5.8% and was slower in all three pairs. This unexplained control regression
prevents an adoption claim. [Recheck samples](g2/recheck/) retain both the
original and additional evidence, with no outlier removal.

Ranges show why small differences should not be overinterpreted: memory CASE
was 489.0–583.3 µs clean, 443.2–533.7 µs static, and 432.2–490.7 µs closures.
All ranges/allocations are in [the G2 summary](g2/summary.json).

## G3 incremental results

The same-source G2 control isolates the loop change. Median microseconds; pair
counts here compare G3 with G2, not clean production.
| Host/query | Clean | G2 | G3 | G3 vs G2 | Faster pairs |
|---|---:|---:|---:|---:|---:|
| memory/arithmetic | 564.54 | 472.90 | 516.12 | +9.1% | 0/5 |
| memory/filter | 519.68 | 469.92 | 484.29 | +3.1% | 2/5 |
| memory/boolean | 642.39 | 543.64 | 531.78 | -2.2% | 2/5 |
| memory/coalesce | 595.50 | 526.26 | 517.76 | -1.6% | 2/5 |
| memory/case | 553.60 | 474.56 | 467.67 | -1.5% | 3/5 |
| file/arithmetic | 531.57 | 482.58 | 481.06 | -0.3% | 3/5 |
| file/filter | 512.11 | 451.72 | 453.44 | +0.4% | 2/5 |
| file/boolean | 651.56 | 532.24 | 535.16 | +0.5% | 1/5 |
| file/coalesce | 574.74 | 526.12 | 512.22 | -2.6% | 4/5 |
| file/case | 537.64 | 492.83 | 492.02 | -0.2% | 3/5 |

G3 adds no material incremental gain on these targets. Its roughly 0–3% changes
on most lanes do not meet the 10% criterion. Memory arithmetic initially
regressed 9.1% against G2, so it was included in the short recheck. The larger
G3 gains against clean production on composed expressions mostly come from G2;
they cannot be credited to loop specialization.

The G3 wrapper is two pointers (16 bytes on this host), one extra allocation per
eligible execution. Arithmetic/CASE/COALESCE therefore use 8,211 allocations
versus G2's 8,210, and composed filtering uses 5,561 versus 5,560. It removes
neither source-row nor output-row allocation. Logical query memory and cost
remain identical. This loop experiment does not solve the dominant allocation
work identified in G1.

The three-set recheck changes memory arithmetic from +9.1% to **-5.5%** versus
G2; file arithmetic is -0.7%. That reversal does not establish a stable loop
benefit. Against clean production, the recheck still has memory first-call
**+3.5%**, file ad-hoc **+3.3%**, and file unsupported **+10.4%**, each slower in
all three pairs. Memory unsupported reverses from +5.6% to -6.0%. Even an
unselected columnar path shows an apparent 18.8% memory gain in G3. These are
unresolved noise/layout/control effects, not evidence that this loop optimizes
columnar execution. No further repetitions were used to chase a preferred
answer. [Recheck evidence](g3/recheck/) and [full ranges](g3/summary.json) are
retained.

A separate 100 ms composed-filter profile attributes about 75% of allocated
bytes to source-row materialization and 9% to the cursor's output rows. This
includes untimed setup allocations and is diagnostic, not a precise steady-state
allocation distribution. Its 210 ms of CPU samples show expression composition,
cost charging, decoding and allocation; the sample is too short for fine-grained
attribution. [Allocation](g3/alloc-top.txt) and [CPU](g3/cpu-top.txt) summaries
are preserved. Escape analysis confirms retained descriptors/closure captures
and the G3 wrapper escape during preparation/setup; private allocation tests
confirm zero added per-expression evaluation allocations.

## Decision and reproduction

**Retain G2 and G3 as opt-in research; do not adopt either as a production
change.** G2 demonstrates a useful composed-filter benefit. Closure-per-node
execution does not consistently improve it and increases preparation allocations.
G3 adds a cursor allocation without a stable incremental speedup. The control
regressions and variability fail the adoption gate. A future investigation should
address source/output allocation and cheap preparation/layout costs before
expanding this expression catalog or attempting batching.

The ordinary build still has no specialization state; G2 uses
`jed_specialization`, closures append `jed_specialization_closures`, and G3
appends `jed_specialization_scan`. Forced and ordinary controls remain separate
build tags, not SQL settings. The [README](../../README.md) lists all commands.
Final engine/timed-test sources match [G3's SHA-256 inventory](g3/environment.json).
For the exact intermediate G2 build, apply [g2/source.patch](g2/source.patch) with `git apply --unidiff-zero` to
G1 commit `90e654fe9b206a5b63d332ea170709e453f5091f`; every file in its
[recorded inventory](g2/environment.json) was checked to match that reconstruction.
The patch includes the then-current harness and tests. G2 was measured before
any G3 source existed, rather than retrospectively disabling G3 in its first
matrix. The final G3 matrix additionally measures the current-source G2 control.

Diagnostics and full correctness logs are in [checks/](checks/). The final three
SQL error-order additions were rerun in all six modes and PostgreSQL after the
full corpus runs. No timing source changed after the final matrix. Retained
artifacts exclude executables and binary profiles; checksums, costs, source
inventories, all timing samples and human-readable profile/escape reports remain.
